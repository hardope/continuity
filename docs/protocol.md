# Continuity protocol (v2)

Status: Phase 0 (protocol core) and Phase 1 (desktop tray app, `continuityd`) are implemented and verified end-to-end on real running processes — mDNS discovery, pairing, clipboard sync, and file transfer all confirmed working, including through the actual `continuityd` binary, not just the `continuityctl` test CLI. Phase 2 (Android) has a complete app built against the shared engine via UniFFI. Phase 3 (iOS) has complete source but is unverified — this dev machine has no full Xcode install. See `docs/android-build.md` and `docs/ios-build.md` for platform-specific detail.

## Identity

Each device has a permanent Ed25519 keypair (`continuity-crypto::Identity`). The hex-encoded public key is the device's `DeviceId`, used everywhere on the wire and as the trust-store key. There is no CA and no account system — the public key *is* the identity.

Storage differs by shell, because there's no portable "OS keychain" API:
- **Desktop** (`continuityctl`, `continuityd`): the `keyring` crate — `apple-native` on macOS, `windows-native` (Windows Credential Manager) on Windows, `sync-secret-service` (GNOME Keyring/KDE Wallet over D-Bus, needs a desktop session) on Linux. `keyring` ships with **zero default features**; forgetting to enable a backend makes it silently no-op instead of erroring, which cost real debugging time early on — see the comment in `continuity-crypto/Cargo.toml`. On Windows, the stored credential's target name follows the `windows-native` backend's default `"{user}.{service}"` convention — `"device-signing-key.app.continuity.identity.{profile}"` — which matters for `installers/windows/continuity.iss`'s uninstaller (see below).
- **Mobile** (Android/iOS via `continuity-ffi`): there's no keychain reachable from Rust on either platform, and no ambient "app config directory" convention `directories` (the crate the desktop shells use for the trust-store path) can guess at. So the FFI layer takes identity bytes and a data directory as constructor arguments instead of deriving them itself — the host app generates the identity once (`generate_identity_der()`) and persists the PKCS8 DER bytes in Android Keystore-backed `EncryptedSharedPreferences` or the real iOS Keychain (Swift talking to its own Keychain item works fine, unlike two different unsigned desktop dev binaries touching the same one — see the ACL discussion in `continuity-crypto`'s identity module history).

**Windows uninstall cleanup (real bug found post-release):** a user reported the Windows uninstaller leaving data behind, requiring manual removal. It did — Inno Setup's default uninstall only removes what's declared in `[Files]` (just `continuityd.exe`), and both the trust store/config and the identity credential are written by the app itself at runtime, in locations Inno Setup has no way to know about on its own:
- trust store + config: `%APPDATA%\continuity\continuity\config` (via `directories::ProjectDirs::from("app", "continuity", "continuity")` — "continuity" appears twice since the same string is used for both organization and application)
- the identity private key: Windows Credential Manager, target name `device-signing-key.app.continuity.identity.default`

Fixed in `installers/windows/continuity.iss`: an `[UninstallDelete]` entry removes the whole `%APPDATA%\continuity` tree, and an `[UninstallRun]` step calls `cmdkey /delete:...` for the credential (harmless if it doesn't exist — e.g. the app was installed but never actually launched, so no identity was ever generated). **Unverified** — no Windows machine in this development environment; this is Inno Setup documentation and `keyring`/`directories` crate source research, not a real uninstall confirmed to leave nothing behind.

## Discovery

mDNS/DNS-SD via `mdns-sd`, service type `_continuity._tcp.local.`. The advertised instance/host name is the first 12 hex chars of the device id (DNS labels cap out at 63 bytes, so the full 64-char id can't be used directly). TXT record carries `id`, `name`, `platform`, `protocol_version`.

Platform notes:
- **Android** needs a `WifiManager.MulticastLock` held at runtime or the OS silently drops incoming multicast packets (`ContinuityForegroundService.acquireMulticastLock`), plus the `NEARBY_WIFI_DEVICES` permission on API 33+.
- **iOS** needs `NSLocalNetworkUsageDescription` and an explicit `NSBonjourServices` entry for `_continuity._tcp` in Info.plist, or local network access silently fails (iOS 14+).

**Refresh (superseded — see below for the current behavior):** the first version of this called `Discovery::refresh()` to re-issue the mDNS query on demand. Real bug found post-release: `mdns_sd::ServiceDaemon::browse()` unconditionally overwrites its single registered listener for a service type ("if there is already a listener, it will be updated, i.e. overwritten" — straight from its own doc comment), so calling it a second time silently orphaned the receiver the engine's own browse loop reads from — refreshing killed *all* further discovery (new devices *and* rediscovery-triggered reconnects) for the rest of the process's life, whether triggered by the periodic ticker or the user's own Refresh click. `mdns-sd` already re-queries on its own via retransmission using the *original* listener, so nothing external was ever needed for that half.

**Current behavior**: `EngineCommand::RefreshDiscovery` and the automatic `spawn_reconnect_ticker` (every `RECONNECT_RETRY_INTERVAL`, 45s) both call `redial_disconnected_trusted_peers` — which never touches mDNS at all, only retries dialing every trusted peer with a cached address (`known_addresses`) that isn't currently connected or mid-dial. This is exposed as the manual "Refresh Nearby Devices" action on both the desktop tray and Android's overflow menu, plus the 45s ticker as a self-heal so a peer that's disconnected but still nearby doesn't need the user to notice and ask.

**mDNS daemon-death recovery**: separately, if the browse task's channel from the `ServiceDaemon` closes for good (the daemon's internal thread crashed or exited unexpectedly) — previously just logged and left discovery dead forever — the browse task now tears down and recreates the whole `Discovery` (fresh `ServiceDaemon`, re-advertise, re-browse), retrying every 5s with a fixed backoff if recreation itself fails (e.g. mid network flap). The new `Discovery` is swapped into `SharedState.discovery` behind a `Mutex` so `EngineHandle::shutdown()` still reaches whichever instance is current.

**Network-change detection**: `spawn_network_watcher` polls the host's local, non-loopback IP addresses every `NETWORK_CHECK_INTERVAL` (10s) via `if-addrs` and sends `EngineCommand::NetworkChanged` when the set changes (Wi-Fi switch, VPN connect/disconnect, cable plug/unplug). That command both recreates discovery (a `ServiceDaemon` created before the change can keep multicasting on an interface that no longer exists) and immediately calls `redial_disconnected_trusted_peers`, rather than waiting for the 45s ticker or the user to notice. A plain poll rather than each platform's native network-change API (macOS `NWPathMonitor`, Android `ConnectivityManager.NetworkCallback`, etc.) deliberately — it's portable, testable code in this one crate, instead of per-platform FFI that would need real Windows/Android hardware to verify (unavailable in this dev environment).

## Transport

TLS 1.3 (rustls) over TCP, with mutual client-certificate authentication — both sides present a self-signed cert generated from their Ed25519 identity (`continuity-crypto::generate_self_signed`). The verifier accepts any cert (there's no CA to chain to) but still performs full cryptographic signature verification during the handshake, so after connecting we know for certain the peer controls the private key behind the cert it presented. The peer's device id is then recovered by parsing the certificate's SubjectPublicKeyInfo (`continuity-net::connection::device_id_from_cert`).

Whether that cryptographically-proven id is *trusted* is a separate, application-level decision — the same split SSH makes between "handshake succeeded" and "host key is known." See Pairing below.

## Connection liveness

**Real bug found post-release:** a peer's message loop only ever exited when `read_message` returned an error — fine for a connection that closes cleanly, but nothing detected a connection that just goes *silent* (wifi drops, the device sleeps, a NAT/router drops an idle UDP/TCP mapping) with no FIN/RST ever arriving. No `SO_KEEPALIVE` was set either. A connection like that stayed in `connected`/`peer_senders` forever from this side's perspective, which meant the mDNS tie-break auto-reconnect logic saw "already connected" and skipped redialing once the peer came back — the reported symptom was "device doesn't reconnect until I restart the app."

Fixed with an application-level heartbeat in `handle_connection_inner`'s message loop: every `PING_INTERVAL` it sends `Message::Ping` (the receiving side already replied with `Message::Pong` — that half existed already, just nothing sent the first ping), and if `CONNECTION_READ_TIMEOUT` passes with no activity at all, the connection is torn down and `SyncEvent::Disconnected` fires, freeing the peer up for the next reconnect. Both constants have been loosened once already from their initial 20s/50s to today's `PING_INTERVAL` = 30s / `CONNECTION_READ_TIMEOUT` = 180s, after the tighter values produced false-positive disconnects in practice.

The first version of this shipped a real logic bug that would have made the whole thing a no-op: it wrapped a fresh `tokio::time::timeout(CONNECTION_READ_TIMEOUT, read_message(...))` around each loop iteration, selected against the ping ticker. Since the ping ticker fired more often than the timeout, the ping branch kept winning the `select!` and recreating that timeout future from scratch before it could ever elapse — a genuinely dead connection would never have been detected, ever. Caught this with an isolated `tokio::io::duplex`-based test (the two constants scaled down for the test, silence on one end, confirming the timeout branch actually fires) *before* it reached the real engine. Fixed by tracking `last_activity: Instant` explicitly and checking `last_activity.elapsed() > CONNECTION_READ_TIMEOUT` on each ping tick instead of re-arming a timeout that a ping shouldn't be resetting in the first place.

While building and testing this, also found and fixed a related gap: `EngineHandle::shutdown()` only aborted the top-level background tasks (mDNS browse, inbound-accept, command loop, the watchers) — it never touched the per-peer connection tasks tracked in `state.connection_handles` (the same map `Reset` aborts everything in), so calling `shutdown()` while the process kept running left every active connection's task running untouched. `EngineHandle` now holds a clone of the engine's `Arc<SharedState>` specifically so `shutdown()` can reach `connection_handles` too.

Verified end-to-end (not just the isolated unit-level test above): two real paired `continuity-daemon` engines, one killed via `shutdown()`, the other correctly fired `SyncEvent::Disconnected` one ping tick past the read-timeout threshold, exactly as designed.

**Write-starves-ping (real bug found post-release):** a large/slow file transfer enqueues every chunk into the same unbounded FIFO channel a `Ping` also goes through, with no priority between them — a ping queued behind a big backlog of chunks doesn't reach the wire until the writer works through that backlog, so the peer never gets it to reply to in time. Since `last_activity` originally only tracked *incoming* messages, the sending side (mostly writing, not reading, during a one-way transfer) could hit `CONNECTION_READ_TIMEOUT` and disconnect itself mid-transfer even though the connection was actively, successfully carrying data the whole time. Fixed by tracking `last_activity` from both a successful read *and* a successful write (shared via `Arc<Mutex<Instant>>` between the reader and writer) — a successful write is just as much proof of a live connection as a successful read, since a truly dead connection's writes eventually fail or block once the OS send buffer and retries are exhausted.

**Writer-task leak on externally-aborted connections (real bug found post-release):** the writer used to run as its own separately `tokio::spawn`ed task holding `write_half`. `tokio::io::split` keeps the underlying stream alive (via a shared `Arc`) as long as *either* half is still referenced — so aborting only the connection's own outer task from outside (`DisconnectPeer`, `Reset`, `EngineHandle::shutdown` — the only abort handle ever tracked anywhere) dropped `read_half` but left the separately-spawned writer task, `write_half`, and the underlying socket running untouched, forever. A real leak on every non-organic disconnect. Fixed by racing the reader and writer as two futures *within the same task* (`tokio::select!` over both, first one to finish wins) instead of a second spawned task — dropping the outer task now drops both halves together, every time.

**Redundant-dial race (real bug found post-release, fixed with a regression test):** `mdns-sd` delivers `ServiceEvent::ServiceResolved` in rapid bursts — one per resolved address/interface for the same peer, commonly a dozen-plus within single-digit milliseconds. The only earlier guard against redialing an already-connected peer was `!connected.contains(peer_id)`, which only becomes `true` *after* a full TLS handshake completes — a window wide enough for several of those burst events to each independently see "not connected yet" and start their own simultaneous dial to the same peer. Each side then resolved which attempt "won" completely independently of the other, with no correlation between the two, so it was entirely possible for this side to settle on attempt #1 while the peer settled on the inbound connection matching attempt #2 — both sides left holding a connection object the other had already abandoned and closed. This read as an immediate, inexplicable disconnect with no relation to file transfers or the keepalive timeout, right after pairing.

Fixed with `try_claim_dial`/`release_dial_claim` — an atomic claim on `SharedState.dialing: Mutex<HashSet<String>>` that every dial path (the mDNS auto-dial loop, manual reconnect, `redial_disconnected_trusted_peers`) must win before spawning a dial task, and must release on every exit path (dial failure, or handing off to `handle_connection` once a connection exists). `HashSet::insert`'s own return value is the actual race-free source of truth; the `connected` check ahead of it is just a cheap non-atomic fast path. Verified with a permanent regression test (`core/continuity-daemon/tests/dial_race.rs`) that runs two real engines through completely natural mDNS auto-dial — the exact path the race used to trigger on — and asserts exactly one clean connection per side with zero disconnects over an 8s-quiet observation window.

Writing that test surfaced one more gap: `EngineHandle::shutdown()`'s `task.abort()` calls are no-ops against the clipboard and now-playing watchers specifically, since both run on tokio's blocking thread pool (`spawn_blocking`) to call synchronous host/FFI code — `abort()` only prevents a *queued* blocking task from starting, and once one is actually executing its closure on its own OS thread, cancellation can't preempt it. Neither watcher's loop had any exit condition, so that thread stayed alive forever, which is exactly what a `tokio::Runtime` waits on when dropped — the regression test above hung well past its own deadline until this was fixed. Fixed with a `shutting_down: AtomicBool` on `SharedState`, set by `shutdown()` before it aborts anything else and checked by both watchers right after they wake from each `std::thread::sleep`, so they notice and exit within one sleep interval instead of never.

**OS-level socket tuning**: every socket (`continuity-net::connection::tune_socket`) now sets `TCP_NODELAY` — this protocol is almost entirely small, latency-sensitive messages, where Nagle's algorithm buffering them to coalesce with "more data soon" only adds latency for no bandwidth benefit — and `SO_KEEPALIVE` (via `socket2`, since tokio's `TcpStream` doesn't expose it directly) as an OS-level safety net *underneath* the application-level ping/pong above. The two are complementary, not redundant: the app-level ping shares the same ordered message stream as everything else the connection carries (so something backed up behind a large queued send could in principle still delay it, even with the read/write activity tracking above), while `SO_KEEPALIVE` probes operate entirely at the OS/TCP level, immune to anything happening in this process's own message queue.

## Connection health in shells

`SyncEvent::PeerActivity { peer_id, seconds_since_activity }` piggybacks on each connection's own `PING_INTERVAL` tick (see above) rather than a separate timer — no new per-connection work, and it's naturally rate-limited to once per peer per ping interval, so a shell can't be flooded by it. It exists so a device list can show something more useful than a binary connected/disconnected dot.

Only Android currently renders it. `MainActivity`'s `DeviceStatus.lastActivityAtMillis` stores a computed wall-clock anchor (`now - secondsSinceActivity * 1000` at the moment the event arrives), not the raw seconds-ago figure — that figure is only accurate the instant the event arrives and goes stale as time passes, whereas an anchor timestamp lets `activityLabel()` recompute "how long ago" fresh against a `nowMillis` state value that ticks every 15s (`LaunchedEffect` + `delay`), independent of whether a new event has actually arrived. Renders as "Active just now" (<20s), "Active Ns ago" (<60s), "Active Nm ago" (<1h), or "Active Nh ago"; falls back to the plain "Connected" label when `lastActivityAtMillis` is still `null` — a peer that just connected hasn't had its first ping tick yet, and "just now" would be a fabricated claim rather than an observed one.

`continuityctl` and `continuityd` both currently no-op this event (see their `handle_event`/`handle_sync_event` match arms) — no tray or CLI surface for it yet, since it fires once per connection per ping interval and isn't worth a log line on every tick in either.

## Framing

Each `Message` (see `continuity-proto`) is sent as a 4-byte big-endian length prefix followed by its JSON encoding (`continuity-net::framing`). Binary payloads (clipboard content, file chunks) are base64-encoded within that JSON rather than left as raw byte arrays — serde's default array-of-numbers encoding for `Vec<u8>` costs 4-5x on wire size, which matters once file chunks are real traffic; base64 costs ~1.33x. Capped at 64MB per message.

### Protocol versions and unknown messages

Every device announces `PROTOCOL_VERSION` (in its mDNS TXT record and `DeviceAnnounce`). Nothing refuses a peer over a mismatch — the number is a capability check, read by whichever side wants to send something newer.

**v1** peers treat *any* message that fails to parse as fatal: their reader loop broke out and dropped the whole connection. Since serde rejects an unknown `type` tag, that meant a v1 peer disconnected the moment a newer peer sent it a message type it didn't know.

**v2** (0.1.6-beta.3 onward) fixes that going forward: a well-framed message that doesn't parse is logged and skipped (`FramingError::Json` in the engine's reader), not treated as a dead connection. That's safe because the length prefix means the whole payload has already been read by the time parsing fails, so the stream is still positioned at the next message — covered by `an_unknown_message_type_leaves_the_stream_in_sync` in `continuity-net::framing`. v2 also adds `ScreenLockRequest`/`ScreenLockResult` (see Remote lock and unlock below). A shell must still only send a post-v1 message to a peer that announced `protocol_version >= 2`, because a v1 peer still drops the connection on it — Android's device page only shows Lock/Unlock for a Linux peer reporting v2+.

## Pairing

Trust-on-first-use with a human-verified confirmation code, modeled on SSH host-key verification / Bluetooth numeric comparison:

1. Both sides exchange `DeviceAnnounce` and cross-check the announced id against the id the TLS handshake already proved (`continuity-net::pairing::announce_and_identify`).
2. Both sides independently compute the same 6-digit code from `SHA-256(sorted(pubkey_a, pubkey_b))` (`continuity-crypto::confirmation_code`) — order-independent, so it doesn't matter who dialed whom.
3. Each user is shown the code and asked to confirm it matches what's on the other screen. Only if *both* sides confirm does the device get added to the local trust store (`continuity-crypto::TrustStore`).

This is a fingerprint-comparison scheme, not a full Diffie-Hellman short-authentication-string exchange. It's sufficient as long as the user actually compares the codes; a stronger ECDH-based SAS (as Signal/Bluetooth SSP use) is a reasonable v2 hardening if this grows beyond personal use.

Already-trusted peers skip straight to step 1 (`announce_and_identify`) with no code prompt — this is the common case in practice (pair once, reconnect silently forever after) and is what lets clipboard/file sync work with zero UI on every subsequent app launch.

## The shared engine

`continuity-daemon::SyncEngine` (started via `continuity_daemon::start`) is the orchestration core — discovery loop, connection dedup/tie-break, pairing handshake, clipboard watch/broadcast, file transfer — shared by every shell:

- `continuityctl` (CLI) and `continuityd` (desktop tray app) call it directly.
- `continuity-ffi` wraps it behind a UniFFI interface (`ContinuityEngine`) for Android/iOS.

It's a channel-driven design, not a trait shells implement: `EngineHandle.events` streams `SyncEvent`s out (pairing requests, connection changes, sync activity) and `EngineHandle.send_command` takes `EngineCommand`s in (`ConfirmPairing`, `SendFile`) — a shell's whole job is translating between that channel and whatever UI toolkit it's built on (stdin prompts, a native tray menu + dialogs, a UniFFI callback interface).

Clipboard access is the one piece the engine doesn't own directly — it takes a `ClipboardBackend` trait object at construction (`ArboardClipboard` on desktop; Android/iOS bridge it through their own `ClipboardProvider`/`ClipboardManager`/`UIPasteboard` code, since there's no cross-platform "background thread OS clipboard" API the way `arboard` provides on desktop).

## Reset and pause

Two `EngineCommand`s every shell exposes (desktop tray menu, Android's overflow menu):

- **`Reset`** — clears the trust store entirely (`TrustStore::clear`) and force-disconnects every active connection. Every peer's task is tracked by an `AbortHandle` keyed on its crypto id specifically so this is possible — a connection is normally just a task blocked reading, with no other way to interrupt it from outside. There's no undo: every previously paired device needs to be paired again from scratch, on both sides. Shells confirm with the user before sending this.
- **`SetPaused(bool)`** — temporarily stops accepting inbound connections, dialing discovered peers, and syncing the clipboard in either direction, without shutting the engine down or dropping connections already open. Checked in four places: the accept loop, the mDNS dial loop, the clipboard watcher, and inbound `ClipboardUpdate` handling. Toggling back off resumes all four immediately; it does not re-sync anything that changed while paused (the clipboard watcher only reacts to changes it observes after resuming, not a diff of what it missed).

Both emit a confirming event (`SyncEvent::WasReset`, `SyncEvent::PausedStateChanged`) rather than assuming the command succeeded — a shell updates its own UI (tray menu label, activity feed) off that event, not off the click that sent the command.

### Revocation

`EngineCommand::RevokeDevice { peer_crypto_id }` forgets one specific paired device — `Reset`'s single-peer counterpart. Addresses a previously-documented gap: revoking used to only remove the peer from the local trust store, without notifying it or closing an existing connection immediately, so a live peer would just sit connected until it happened to drop on its own.

Now: removes the peer from the trust store, and — best-effort, if currently connected — sends `Message::Revoked` before force-closing the connection. Revocation is deliberately **one-directional**, the same way an SSH host removing a key from `authorized_keys` doesn't touch the client's own `known_hosts`: the receiving side does *not* automatically forget the revoker back. It emits `SyncEvent::RevokedByPeer` instead, so a shell can tell the user why the connection just dropped and stopped auto-reconnecting, and the user can decide whether to revoke back.

**A real race in the notify step, caught by the regression test below:** queuing `Message::Revoked` onto the connection's writer channel and then immediately aborting the connection task has no `.await` in between — the writer task never gets a scheduler turn to actually flush the message before its task dies, so naively doing both back-to-back means the notification is dropped essentially every time, not just occasionally. Fixed by spawning the abort+cleanup as a separate task with a short (150ms) delay first when there was something to send, rather than blocking the shared command-processing loop (which handles every other `EngineCommand` too) on that delay inline.

Once revoked, the peer isn't specially blocked from reappearing — since the mDNS auto-dial loop already only dials *trusted* peers (see Discovery above), removing the trust entry is sufficient; if the revoked device is still nearby, it just shows back up as an untrusted `PeerDiscovered`, like any other never-paired device.

Exposed as a "Forget" action per-device: Android's device list, desktop's new "Forget Device" tray submenu (mirroring the existing per-device "Send File" submenu), and `continuityctl`'s `revoke <id>` REPL command. Verified with a permanent regression test (`core/continuity-daemon/tests/revoke.rs`, following the same real-two-engines pattern as `dial_race.rs`): revoking a connected peer produces exactly one `WasRevoked` on the revoking side and exactly one `RevokedByPeer` + `Disconnected` pair on the revoked side.

### Desktop confirmation dialogs (Linux)

**Real bug found post-release, reported as two seemingly unrelated symptoms** — "Reset doesn't bring up the confirm dialogue" on Linux, and separately "a Mac connecting to Linux doesn't show anything on the Linux side" — that turned out to be the exact same root cause. `continuityd` uses `rfd::MessageDialog` for both the Reset confirmation and the pairing-request accept/decline prompt (see Pairing above). `rfd`'s default Linux backend is the XDG Desktop Portal, which has **no message-dialog API at all** — for `MessageDialog` specifically, `rfd` falls back to shelling out to the external `zenity` binary, which most systems don't have installed by default. With `zenity` missing, both dialogs silently do nothing, which reads as "the confirmation just never appears" from either flow.

Fixed by giving `continuityd` a real, directly-linked GTK3 implementation on Linux instead — `rfd`'s `gtk3` feature covers both `MessageDialog` and `FileDialog`, so this isn't Linux-specific to just the dialogs that were broken. GTK is already a hard runtime dependency on Linux regardless, since `tray-icon` needs it for the tray icon itself, so this adds no new system requirement, and no `zenity` dependency is needed either now that nothing falls back to it.

This went through one real iteration first: `gtk3` and `xdg-portal` looked additive (Cargo generally unions feature requests for the same dependency), so the first attempt just added a Linux-only `rfd = { features = ["gtk3"] }` on top of an unconditional `rfd = "0.15"` (implying its default `xdg-portal` feature) used for file dialogs on every platform. `rfd`'s own `build.rs` hard-panics if both end up enabled at once — and since Cargo's feature unification isn't scoped by target `cfg`, that unconditional declaration's default features were still being requested on Linux regardless of the target-specific override, so both were enabled together. CI's Linux build caught this immediately (`You can't enable both 'gtk3' and 'xdg-portal' features at once`). Fixed by giving Linux its own complete, target-scoped `rfd` declaration (`default-features = false, features = ["gtk3"]`) and moving the unconditional one behind `cfg(not(target_os = "linux"))` instead, so the two declarations never both reach the same build.

**Unverified beyond CI compiling successfully** — no Linux machine available in this development environment; the underlying fix is code/dependency-research-based (`rfd`'s own source and Cargo feature docs), not confirmed against a real Linux desktop.

## Clipboard sync

Mesh, not hub-and-spoke: every device keeps a persistent connection to every currently-online trusted peer and pushes `ClipboardUpdate` to all of them when its own OS clipboard changes (the engine's watcher polls the injected `ClipboardBackend` every 500ms).

**Loop prevention**: a device never re-broadcasts a `ClipboardUpdate` it received — only clipboard changes its *own* watcher detects get sent out. To stop the watcher from treating its own programmatic write (applying a peer's update) as a new local change and re-broadcasting it, every remote-triggered write is hashed and recorded before it's applied; the watcher compares against that hash and skips the echo.

**Integrity check**: every `ClipboardUpdate` carries a content hash; receivers recompute it and drop the message if it doesn't match, rather than trusting the sender's claim.

**Platform caveats** (not bugs — real OS restrictions, see the per-platform build docs for detail):
- **Android**: background clipboard *reads* are restricted to the foreground app since Android 10, so outbound sync is reliably live only while the app is foregrounded, even though the mesh connection itself stays up via the foreground service. Writing (receiving a peer's update) isn't restricted the same way.
- **iOS**: outbound watching is disabled entirely for now (`IosClipboardProvider.getText()` always returns `nil`) — polling `UIPasteboard` at the engine's 500ms interval would trigger the system's "pasted from Clipboard" privacy banner about twice a second while the app is open. Receiving still works. See the doc comment in `apps/ios/Continuity/IosClipboardProvider.swift`.

## File transfer

Explicit point-to-point, not broadcast: the sender picks a target device and calls `EngineCommand::SendFile`; the receiver auto-accepts from trusted peers (only a paired device can reach this code path at all) up to a 500MB cap, streams the file to disk in 64KB chunks, and verifies an end-to-end content hash before reporting it received.

- `FileOffer` → receiver creates the destination file and replies `FileAccept`
- `FileChunk` × N → written straight to disk with `tokio::fs`, hashed incrementally (`continuity_crypto::IncrementalHash`) so the whole file never needs to sit in memory on the receive side (the send side does currently read the whole file into memory to compute one hash up front — fine for the file sizes this is built for, a real limitation for very large files)
- `FileComplete` → receiver compares its incremental hash against the sender's claimed one; mismatch deletes the partial file and reports failure instead of a corrupt result

Verified end-to-end between two `continuityctl` instances (real file, content diffed byte-for-byte after transfer) and wired into `continuityd`'s tray menu ("Send File to `<connected device>`...", via a native file picker).

## Media control

`Message::MediaCommand` (`PlayPause` / `Next` / `Previous` / `VolumeUp` / `VolumeDown` / `Seek { position_ms }`) is fire-and-forget, no acknowledgement — a mobile shell sends it via `EngineCommand::SendMediaCommand { peer_crypto_id, command }`, the receiving engine hands it to whatever `MediaController` its shell wired in at startup (`continuity_daemon::MediaController` trait, mirroring `ClipboardBackend`'s pluggable-per-platform shape). Volume is still step-based to *control* (`VolumeUp`/`VolumeDown`, not "set to X%") — deliberately matching how a physical keyboard's volume keys work — but is now also *read back*: `NowPlayingInfo::volume_percent` (see below) reports the actual current level, so a shell can show it without needing a "set absolute volume" command. `Seek` is the one genuinely absolute command here, since a relative "jump forward/back" gesture isn't what a drag-to-scrub UI naturally produces.

**macOS** (`MacMediaController`, `core/continuityd/src/media_mac.rs`) — verified against real playback, not just type-checked. Transport (play/pause/next/previous) constructs a synthetic `NSEventTypeSystemDefined` event carrying one of the `NX_KEYTYPE_PLAY`/`NX_KEYTYPE_NEXT`/`NX_KEYTYPE_PREVIOUS` constants from `IOKit/hidsystem/ev_keymap.h` and posts it at the session level — the same trick every macOS media-key-simulation tool has used since `SPMediaKeyTap`, since there's no public documented API for "control whatever's currently playing." Confirmed against a real QuickTime Player session (`playing` toggled true→false in response to the synthetic key, checked via AppleScript). Volume does *not* use the same synthetic-key trick — `NX_KEYTYPE_SOUND_UP`/`DOWN` had zero measurable effect on real output volume across repeated test presses — so it instead goes through raw CoreAudio (`AudioObjectGetPropertyData`/`SetPropertyData` on `kAudioDevicePropertyVolumeScalar`), with a per-channel (element 1/2, stereo L/R) fallback added after this dev machine's output device turned out not to expose the "main" element-0 volume property at all. Confirmed with a real ±6.25% round trip via `osascript -e "output volume of (get volume settings)"`. Seeking goes through `MRMediaRemoteSetElapsedTime` (same private-framework `dlopen` pattern as reading now-playing info, see below).

**Accessibility permission gate (macOS, real bug found post-release):** `CGEventPost`ing a synthetic media key is gated behind Accessibility trust (`AXIsProcessTrusted`) — CoreAudio volume calls aren't gated at all, which is exactly the asymmetry a user reported ("volume works, play/pause/next/prev do nothing"). An ad-hoc-signed build starts out untrusted, and since TCC tracks trust per code signature, a rebuilt ad-hoc binary can lose a previously-granted grant. Reproduced locally: `AXIsProcessTrusted()` returned `false` on this dev machine even though the exact same test binary had previously toggled QuickTime's play state in an earlier session — and with it `false`, a real playing browser tab's play state didn't budge. `post_media_key` now calls `ensure_accessibility_trust()` once per process (`std::sync::Once`, so it doesn't spam a notification on every remote tap): if untrusted, it logs a clear warning, shows a system notification, and opens System Settings straight to the Accessibility pane via `open x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility` (confirmed this actually opens the pane, not just documented to). This can't grant the permission itself — only the user can flip that toggle — but it turns a silent, confusing no-op into a discoverable, actionable one.

**Windows** (`WindowsMediaController`, `core/continuityd/src/media_windows.rs`) — transport still goes through `SendInput` with the standard `VK_MEDIA_PLAY_PAUSE`/`VK_MEDIA_NEXT_TRACK`/`VK_MEDIA_PREV_TRACK`/`VK_VOLUME_UP`/`VK_VOLUME_DOWN` virtual keys, exactly what a keyboard's own media keys send. Volume *readback* and seeking are newer additions on two different, unrelated APIs: volume through the Win32 `IAudioEndpointVolume` COM interface (SMTC has no volume surface of its own — same split as macOS's separate CoreAudio route), seeking through WinRT's `GlobalSystemMediaTransportControlsSession::TryChangePlaybackPositionAsync` (see Now-playing metadata below for why this needed a real bug fix, not just a new call). **Not verified against a real playing session** — there's no Windows machine in this development environment, only CI's `windows-latest` runner, which confirms it compiles against the real Windows SDK but not that it behaves correctly.

**Linux** (`LinuxMediaController`, `core/continuityd/src/media_linux.rs`) — MPRIS over D-Bus (`org.mpris.MediaPlayer2.Player`'s `PlayPause`/`Next`/`Previous` methods and `Volume`/`Position` properties), via `zbus`'s blocking API. MPRIS has no single "the current session" the way macOS/Windows do — every player registers its own bus name, and more than one can be running — so this targets whichever `org.mpris.MediaPlayer2.*` name is found first, a known, real limitation shared with most simple MPRIS tools. Seeking uses MPRIS's relative `Seek(offset)` method rather than its absolute `SetPosition(TrackId, Position)`, deliberately — per spec, `SetPosition` silently no-ops if the given track id doesn't exactly match whatever the player considers current, a real footgun for a fire-and-forget command with no acknowledgement to detect that against; `Seek`'s offset (computed from a freshly-read current position) has no such requirement. **Not verified against a real playing session** — no Linux desktop environment with a real media player in this development environment, only CI's headless `ubuntu-latest` runner, which confirms compilation, nothing more.

### Now-playing metadata

`Message::NowPlayingUpdate { info: NowPlayingInfo }` (title/artist/album/artwork/`is_playing`/`position_ms`/`duration_ms`/`volume_percent`) is pushed unprompted, not a response to anything — `MediaController::now_playing()` is polled by `spawn_now_playing_watcher` in the engine every 1.5s (same shape as the clipboard watcher: dedupe against the last-seen value, broadcast to every connected peer on change — `position_ms` changing on essentially every poll while something is playing means this now broadcasts nearly every tick during playback, which is the *correct* behavior here, not a regression: a receiver's progress bar needs a real update that often to track playback without drifting), and a change to `None` (nothing playing / source app quit) still gets broadcast as an empty/default `NowPlayingInfo` rather than silently skipped — otherwise a peer's display would keep showing stale info forever once playback actually stopped.

macOS reads this from `MediaRemote.framework` (also private, same `dlopen`/reverse-engineering situation as the media-key trick) — `MRMediaRemoteGetNowPlayingInfo` on a GCD global concurrent queue (deliberately *not* the main queue: that only executes queued work when something is actively pumping a run loop, which isn't guaranteed in every context this can run from, e.g. it never fired at all when first tested from a bare `cargo test` binary — a global queue has its own worker thread pool and doesn't depend on that), parsing the returned `CFDictionary` by the well-known `kMRMediaRemoteNowPlayingInfo*` string keys. Verified against real playback, not just type-checked: dumped an actual returned dictionary's keys to confirm the naming convention, and watched `is_playing` correctly track true/false against a live QuickTime Player session.

**Elapsed-time snapshot gap (real bug found while adding position tracking, macOS):** `kMRMediaRemoteNowPlayingInfoElapsedTime` reads back as a frozen value, not a live one — confirmed by hand: it stayed exactly `0` across multiple polls seconds into real playback. It's a *snapshot*, paired with `kMRMediaRemoteNowPlayingInfoTimestamp`, pushed only on discrete events (play, pause, seek, track change) rather than continuously — the same design every real MediaRemote-based "now playing" tool works around by interpolating client-side. Fixed by computing the true live position as `snapshot elapsed + (now - snapshot timestamp)` while playing (unchanged while paused, since nothing's advanced since the snapshot), clamped to the track's duration so a stale snapshot read past a loop/track-end doesn't show a progress bar stuck over 100%. Re-verified after the fix: position correctly advanced from the snapshot and clamped exactly at the track's own duration on a real (looping) clip.

Windows reads this via the public WinRT `GlobalSystemMediaTransportControlsSessionManager` API (`RequestAsync` → current session → `TryGetMediaPropertiesAsync`/`GetPlaybackInfo`), with artwork pulled from the session's `Thumbnail` stream reference, and position/duration via `GetTimelineProperties()`. The same stale-snapshot-needs-interpolation issue confirmed by hand on macOS is *documented* by Microsoft to apply here too (`Position` is relative to `LastUpdatedTime`, not live) — the same `position + (now - LastUpdatedTime)` correction is applied, but this specific piece is unverified on real Windows, unlike its macOS equivalent. Linux reads metadata from the same MPRIS `Player` interface used for transport control — its `Metadata` property dictionary (`xesam:title`/`artist`/`album`, `mpris:artUrl`, `mpris:length`) and `PlaybackStatus`/`Position`/`Volume` properties; artwork is only read when `mpris:artUrl` is a `file://` path (MPRIS gives a URL, not raw bytes, and fetching an arbitrary remote URL on every 1.5s poll isn't something to do silently), empty otherwise. Unlike macOS/Windows, MPRIS's `Position` is specified as always reflecting the actual current position when read — no interpolation needed. Both Windows and Linux metadata reads are unverified against real playback for the same reason their transport-control halves are (no local Windows/Linux desktop environment) — CI compile-checks only, so far.

Android shows a one-line "now playing" title/artist and a play/pause button on each desktop device's card, and the full player on that device's own page (tap the device — it opens whether or not anything is playing; with nothing playing, the transport buttons still work, since play can resume whatever was playing last). Both are shown only for peers reporting a platform whose `MediaController` isn't the no-op default (macOS/Windows/Linux). The player has album art (decoded from the raw artwork bytes), a draggable progress slider (sends one `Seek` on release, not continuously while dragging) and a read-only volume level bar (hidden gracefully when `volume_percent` is `null` — a platform that doesn't report a level, not "definitely at 0%"). Since the watcher only pushes a real update every 1.5s, the progress bar animates forward client-side between updates using the device's own clock (the same anchor-timestamp technique as `SyncEvent::PeerActivity`'s "active Ns ago") rather than visibly jumping once per tick.

## Remote control

Full remote control of a paired desktop's keyboard, mouse, and screen — architecturally the biggest addition to this protocol since the original pairing/sync/file-transfer core. Three deliberate scope boundaries shape everything below:

- **Android/iOS are controllers only, never a controllable target.** Injecting system-wide input on Android needs a user-granted Accessibility Service, and capturing its screen needs `MediaProjection` with a permanently-visible notification — both much heavier, more intrusive grants than anything else this app asks for, for a capability (remote-controlling a *phone*) far less useful than the reverse. Enforced not just by omitting UI, but structurally: `continuity-ffi` always wires in `NoopRemoteControlHost`, whose `is_available()` returns `false`, so an inbound request against a phone is auto-declined by the engine itself.
- **A live mirror, not a true extended desktop.** "Use the second device as a secondary display" means an always-on view of the controlled screen, not a real second monitor a window manager could place windows onto — the latter needs a virtual display driver (on Windows, a *signed kernel driver*), a completely different risk/complexity tier this project isn't taking on.
- **JPEG-frame streaming, not a hardware video codec.** Real low-latency video (H.264/VP9 with a proper encoder pipeline) is roughly its own project. Each frame here is a complete, independent screenshot — simpler to implement correctly across three platforms with zero ability to test two of them, at the cost of the bandwidth efficiency a real codec's delta-frame encoding would give.

### Consent is separate from pairing

Being an already-paired, trusted peer proves *identity* — it says nothing about whether this specific, much larger grant (type and click as this device, watch its screen) is welcome. The first `Message::RemoteControlRequest { session_id }` from a given peer requires an explicit accept on the controlled side (`SyncEvent::RemoteControlRequested` → `EngineCommand::RespondToRemoteControlRequest`); since 0.1.5 that accept is remembered for that peer (`TrustStore::allow_remote_control`), so later requests start straight away until the device is forgotten. `session_id` (a random hex string, generated by whichever side calls `EngineCommand::RequestRemoteControl`) is carried on every message for that session from then on, so a stale message from an already-ended session is unambiguous and gets dropped rather than misapplied to whatever session happens to be active now.

A device can only be in *one* session at a time, in *either* role — `SharedState.remote_control_sessions` is keyed by peer id, not session id, and accepting a second `Controlled`-role request while one's already active is declined outright rather than accepted into a state `RemoteControlHost`'s single capture on/off switch can't actually represent (two different peers fighting over the same cursor). A shell never tracks `session_id` itself — every command (`RequestRemoteControl`, `SendInputEvent`, `EndRemoteControlSession`, ...) takes just `peer_crypto_id`, and the engine resolves whichever session is current for that peer internally.

### Input relay

`Message::InputEvent { session_id, event: InputEventKind }` carries one `KeyDown`/`KeyUp`/`MouseMove`/`MouseButton`/`MouseScroll` over the *existing* mesh connection — small, ordered, latency-sensitive, exactly what that connection already handles well. Key codes are the controlled platform's own native codes (`CGKeyCode` on macOS, `VIRTUAL_KEY` on Windows), not translated through a shared cross-platform enum — there's always exactly one real sender and one real receiver per event, so a neutral intermediate format would only add a lossy translation layer for no one. Mouse coordinates are normalized `0.0..=1.0` (top-left origin) rather than raw pixels, so the controller never needs to know the controlled screen's actual resolution up front.

**macOS** (`MacRemoteControlHost`, `core/continuityd/src/remote_control_mac.rs`) injects via `CGEventPost` — the exact mechanism `media_mac.rs` already uses for media keys, just building full `CGEventCreateKeyboardEvent`/`CGEventCreateMouseEvent`/`CGEventCreateScrollWheelEvent2` events instead of the three fixed `NX_KEYTYPE_*` constants. Gated behind the same Accessibility permission as media keys (calls the same shared `ensure_accessibility_trust()`, not a separate prompt) — **confirmed by hand this gate is real, not just documented**: with this dev machine's test binary untrusted, a posted `MouseMove` constructed and posted without error, but the real system cursor never moved. The event-construction and coordinate-scaling code itself compiles and passes review but is otherwise unverified end-to-end, pending a trusted binary — granting Accessibility trust needs a human clicking through System Settings, which this environment can't do non-interactively (a `cargo test` binary's code signature, and therefore its TCC identity, changes on every rebuild).

**Windows** (`WindowsRemoteControlHost`, `core/continuityd/src/remote_control_windows.rs`) injects via `SendInput`, the same call `media_windows.rs` already uses for media keys. Mouse movement uses `MOUSEEVENTF_ABSOLUTE`, whose coordinates are natively normalized `0..=65535` regardless of real screen resolution — lines up with this protocol's own `0.0..=1.0` almost for free, just a different scale factor. **Not verified against a real Windows session** — same caveat as every other Windows-only file in this codebase.

**Linux** (`LinuxRemoteControlHost`, `core/continuityd/src/remote_control_linux.rs`) goes through the xdg-desktop-portal `RemoteDesktop`/`ScreenCast` D-Bus interfaces rather than classic X11/XTest — the deliberate choice, since XTest simply doesn't work at all under a native Wayland session (the default on current GNOME/Fedora/Ubuntu), while the portal works under both native Wayland and X11-via-XWayland. Unlike macOS/Windows's synchronous, permission-granted-once model, this is an inherently async flow: `CreateSession`/`SelectDevices`/`SelectSources`/`Start` each round-trip through a `Request` object and its `Response` signal, and `Start` is what shows the user a real system "Share your screen and control input?" dialog — on every session, not just once (persistence across sessions is a portal-level concern this doesn't attempt yet). Input injection uses `NotifyKeyboardKeycode`/`NotifyPointerMotionAbsolute`/`NotifyPointerButton`/`NotifyPointerAxis` with raw Linux evdev codes (`KEY_*`/`BTN_*` from `input-event-codes.h`) — a different numbering entirely from `CGKeyCode`/`VIRTUAL_KEY`. Screen capture negotiates a PipeWire video stream via `OpenPipeWireRemote` and the `pipewire` crate (`MainLoop`/`Context::connect_fd`/`Stream`, format negotiation via a hand-built `SPA_PARAM_EnumFormat` POD, BGRx/RGBx/BGRA/RGBA all supported); `cursor_mode: Embedded` means the compositor bakes the real system cursor directly into the stream, so — unlike Windows' `GetCursorInfo`/macOS's synthetic marker — there's no separate cursor-compositing step at all. The D-Bus/portal half is checked against the real, versioned interface XML; the PipeWire half is checked against the `pipewire`/`libspa` crates' own real source. Both halves have actually been **compiled** against a genuine `libpipewire`/`libspa` 0.3.65 and real D-Bus headers (via a disposable Linux container with the real dev packages installed, isolating just this file's dependency graph from the rest of the workspace to keep the build fast) — this caught and fixed three real bugs: a `pw` import alias scoped too narrowly to reach two module-level items, and a `.cloned()` call on `zbus::zvariant::OwnedValue`, which turns out not to implement `Clone` at all in zbus 4.4. What's still **not verified is runtime behavior against a live compositor** — no real Wayland session in this dev environment, so format negotiation and frame decoding in particular are the most likely things left to need a fix once run on the user's own Linux box.

**The portal handshake never completed (real bug, reported on Ubuntu 26.04.1, fixed in 0.1.6-beta.5):** a session from the phone sat on "connecting" forever. Every portal step answers through a `Request` object's `Response` signal, and the code listened on a *predicted* request path built from a `handle_token` it never actually passed — so the portal chose its own token and answered on a path nobody was listening to, and the very first call (`CreateSession`) waited forever. It also built the session path without the required sender element (`/org/freedesktop/portal/desktop/session/SENDER/TOKEN`). The portal client now lives in `remote_control_linux/portal.rs`, kept free of PipeWire so it builds anywhere zbus does, and was run against a mock portal over a real D-Bus connection — which reproduces the old hang exactly, and covers approval, decline, timeout, cancellation, a desktop with no `RemoteDesktop` portal, and a portal refusing persistence. Fixed alongside it:
- **Pointer coordinates** were sent as the phone's normalized `0..1` values, which the portal reads as pixels — every tap landed in the top-left corner. They're now scaled to the space each desktop expects: mutter divides them by the monitor's scale (`meta_screen_cast_monitor_stream_transform_position`), so on GNOME they're the stream's own pixels — the PipeWire frame size; KDE's portal adds them to the output's logical position, so there they're the portal-reported `size`. The portal spec says logical; mutter, which GNOME and Ubuntu run, doesn't.
- **Input ordering**: each event used to be its own spawned task, so a click could overtake the move before it. One task now delivers a session's input in order.
- **Pacing**: frames were JPEG-encoded at full resolution for every compositor frame (up to the monitor's refresh rate). The stream now negotiates a maximum framerate of 10/s, matching macOS/Windows, and mutter sends a follow-up frame for any change it held back; frames wider than 1920px are scaled down by a whole factor before encoding; only the newest queued buffer is encoded. The framerate range offered is also open-ended now — it used to cap at 60/1, which a producer reporting a higher refresh rate would have failed to negotiate.
- **Approval**: `Start` (the step that shows the desktop's own dialog) gives up after 90 seconds and takes the dialog back down (`Request.Close`, then `Session.Close`); ending the session from the phone while the dialog is up does the same. Where the portal supports it (`RemoteDesktop` v2), the session asks to persist, and the restore token is kept next to the trust store (`remote-desktop-restore-token.<profile>`, readable only by the user), so after the first approval later sessions can start without the dialog. Continuity's own per-device consent still applies first.
- **Stopping from the desktop**: the portal closing the session (GNOME's "Stop sharing") ends the capture with a reason the phone shows.

### Screen capture and the dedicated stream connection

Screen frames get their own **separate TCP+TLS connection**, never the peer's existing mesh connection — a real, foreseeable stability risk motivated this: a continuous stream of frames sharing the same per-connection message queue as clipboard/file/ping traffic is exactly the "write-starves-ping" bug class already found and fixed once this session (see Connection liveness above), just worse, continuously, instead of during an occasional large file transfer.

The controlled side dials this second connection itself, once accepted and once its capture has produced a first frame, to the controller's already-known mDNS-discovered address. Waiting for that frame matters on Linux, where capture can still fail after `RemoteControlHost::start_capture` returned (the desktop's own approval dialog can be declined or go unanswered): the session then ends over the mesh connection with `Message::RemoteControlEnded { session_id, reason }` carrying the host's `capture_failure_reason()`, rather than leaving the controlling side with an unexplained closed stream. `reason` is optional and omitted when empty, so it needs no protocol version. When a stream that did start stops on its own, the same message goes out before the stream connection closes, and the controlling side waits `SCREEN_STREAM_END_GRACE` (750ms) after a stream closes for it to arrive before calling the end unexpected. It skips the normal `announce_and_identify` handshake entirely — identity is already fully proven by the TLS client certificate alone (`Connection::peer_device_id()`, exactly what `announce_and_identify` itself cross-checks against), so a second round-trip would confirm nothing a redundant read wouldn't already pay for. Its first (and only JSON) message is `Message::ScreenStreamHandshake { session_id }`; every message after that is raw length-prefixed bytes (`continuity_net::framing::write_frame`/`read_frame`), not JSON — skipping JSON encoding and this protocol's usual base64 binary-in-JSON convention specifically because a continuous 10-15fps stream pays that ~1.33x overhead on *every single frame*, not just occasionally the way a file chunk does.

The accept loop recognizes an inbound screen-stream connection **by identity alone**, not by peeking at what it sends: `SharedState.pending_screen_stream_peers` records exactly which peer id this device is expecting one more inbound connection from (populated the moment a `RemoteControlResponse { accepted: true }` arrives on the controlling side), so there's no added latency or message-inspection on the far more common case of a normal reconnect.

Frame delivery is deliberately **lossy under backpressure**: `RemoteControlHost::start_capture()` returns a channel the platform capture loop feeds with `try_send` (drops the frame if the channel's full) rather than a blocking send — an old frame that missed its window is worthless once a newer one exists, and blocking would stall capture's own timing instead of just skipping ahead. `push_screen_stream` (the controlled side's forwarding loop) simply drains whatever the channel gives it onto the wire.

**macOS** captures via `CGDisplayCreateImage` — deprecated in favor of ScreenCaptureKit, but a single synchronous call versus ScreenCaptureKit's async, delegate-based streaming API that would need substantially more hand-written Objective-C interop to bind correctly from Rust with no way to iteratively verify it beyond this one real Mac. JPEG encoding goes through `NSBitmapImageRep`'s standard `representationUsingType:properties:` export (the same Apple-blessed path any macOS screenshot tool uses) rather than hand-rolling `CGImage`'s raw pixel-format handling. **Verified for real**: `print_screen_capture_info` confirms a genuine JPEG comes back (327KB at this display's resolution) — capture works end to end.

**Windows** captures via classic GDI `BitBlt` into a memory device context, `GetDIBits` to pull the raw BGRA pixels back out, then the pure-Rust `image` crate for the JPEG encode itself — deliberately not Windows' own WIC (Windows Imaging Component) COM API, which would be more unverifiable COM interop surface, and deliberately not the newer Desktop Duplication (DXGI) API, which needs a real Direct3D device and adapter enumeration where GDI's screen-to-memory blit has worked unchanged since Windows 95 with no device setup at all. **Not verified against a real Windows session.**

### Android's controller UI

`RemoteControlScreen` in `MainActivity.kt`: the live JPEG frame decoded and displayed full-screen, a **direct** tap/drag-to-mouse mapping (touch position maps straight to the equivalent normalized point on the controlled screen — tap to click, drag to move — not a relative "trackpad" mode, which would need tracking a virtual cursor position client-side; simpler to get right at the cost of precision on a small phone screen controlling a much larger desktop), and a basic on-screen-keyboard bridge: a real, minimally-visible `BasicTextField` the IME can type into, diffed against its previous value on every change (new characters → `KeyDown`/`KeyUp`, a shrinking value → `Backspace`) and cleared back to empty after every keystroke so it relays individual keys rather than accumulating its own text buffer.

Keyboard support is intentionally basic for this version: lowercase letters, digits, space, enter, and backspace only (`macKeyCodeFor`/`windowsKeyCodeFor`/`linuxKeyCodeFor` in `MainActivity.kt`) — no shift/uppercase/symbols/arrow keys yet. Enough for a URL or a quick search, not a substitute for a full keyboard.

The "Remote Control" action appears for connected macOS/Windows/Linux peers (not Android/iOS peers, who'd just auto-decline). **Real bug fixed in 0.1.6-beta.5:** the engine's `detect_platform` only recognized macOS and Windows, and Android's `target_os` is `"android"`, not `"linux"` — so every phone announced itself as Linux, and another phone offered remote control, media and lock/unlock for it. Phones now announce `android`/`ios`; one still running 0.1.6-beta.3 or older keeps announcing Linux until it's updated. Confirmed to compile and build into a real APK; live end-to-end verification against a real paired connection hit the same emulator-networking wall as the media progress bar (see Known gaps below) — the underlying protocol/session logic is covered instead by a real two-engine integration test (`core/continuity-daemon/tests/remote_control.rs`) using a fake-but-functional `RemoteControlHost` test double, since real screen capture and input injection need OS permissions this environment can't grant non-interactively either way.

Any desktop platform can be the *controlling* side, not just the two/three that can be a controllable target — the viewer window (`RemoteViewer`, `core/continuityd/src/remote_viewer.rs`, a `tao` window with a `softbuffer`-drawn pixel buffer) is cross-platform and gated only on the `remote-control` feature, not `target_os`. The desktop tray's "Remote Control" submenu lists connected desktops only (a peer whose platform isn't known yet is left in). It's currently hidden from the tray menu: mac-to-mac testing found the controlling app freezing once a session started, and the entry stays out until that's tracked down.

### Lite builds

The `remote-control` Cargo feature on `continuityd` (default-on) gates the real macOS/Windows/Linux `RemoteControlHost` implementations and their platform dependencies (ScreenCaptureKit/AppKit imaging APIs, GDI, the `image` crate, `zbus`/`pipewire`) — a "lite" build passes `--no-default-features` and gets `NoopRemoteControlHost` instead, compiled in at the source level, not just hidden behind a disabled button. The protocol types themselves (`Message::RemoteControlRequest` and friends) are *not* feature-gated — they live unconditionally in `continuity-proto`, so a lite build still understands and correctly auto-declines a request from a full peer, rather than the two builds becoming wire-incompatible.

## Remote lock and unlock

`Message::ScreenLockRequest { action: Lock | Unlock }` asks the receiving device to lock or unlock its own screen; it answers with `Message::ScreenLockResult { action, outcome }`, where `outcome` is `done`, `not_allowed`, `unsupported`, or `failed { reason }`. Requires protocol v2 on the receiver (see Protocol versions above). A shell sends it with `EngineCommand::RequestScreenLock` and gets the answer back as `SyncEvent::ScreenLockResult`.

**Consent model.** Unlike remote control, there's no prompt at request time — for an unlock, by definition, nobody's at the computer to answer one. Consent is given ahead of time, on the computer itself, per device: `TrustStore::set_unlock_allowed` (persisted as `unlock_allowed` in the trust file, off by default for every device, never implied by pairing or by remote-control consent, refused for an unpaired device, and dropped by `revoke`/`clear` along with everything else about a device). The desktop tray turns it on from **Allow Remote Unlock** (Linux only, the one platform that can be unlocked), and asks for confirmation before turning it *on*. That menu lists every connected device plus any device that's allowed while offline, since a lost phone is exactly the one whose permission most needs to be easy to take back (the engine emits `SyncEvent::UnlockPermissionChanged` for each allowed device at startup for this). Lock needs no grant — any paired device can lock the screen, since that only makes the device more secure. Every request is reported to the local user afterward via `SyncEvent::ScreenLockRequested`, *including refused ones*: the tray shows "'Pixel' unlocked this computer", or that a device tried to unlock it without permission. On the phone, Unlock asks for confirmation first, since a stray tap would otherwise unlock an unattended computer.

**Linux** (`LinuxScreenLock`, `core/continuityd/src/screen_lock_linux.rs`): systemd-logind's own `Lock()`/`Unlock()` on this user's graphical session object, over the system D-Bus — exactly what `loginctl lock-session`/`unlock-session` call. logind lets a session's own user do this without a polkit prompt, and the daemon runs as that user, so it gets exactly that and nothing more. The session is found from `XDG_SESSION_ID`, then by PID, then via the user's primary display session (`org.freedesktop.login1.User.Display`) — the last one matters because GNOME and other systemd-managed desktops start autostart apps in their own systemd scopes, outside the session's process tree. logind doesn't draw the lock screen itself, it signals the desktop's locker: GNOME Shell and KDE Plasma honor that; some standalone lockers (swaylock, i3lock) don't. Since `Unlock()` "succeeds" either way, the controller then watches the session's `LockedHint` for up to 3s and reports `failed` with an explanation if the lock screen never went away. Only compile-checked so far (no live logind graphical session in this dev environment), like the rest of the Linux backends.

**macOS and Windows** answer `unsupported`: neither has a supported API for an ordinary app to dismiss its lock screen.

The engine-side consent gating and routing is covered by a real two-engine test (`core/continuity-daemon/tests/screen_lock.rs`, with a fake controller): refused until allowed, the controller never called on a refused request, lock without a grant, `unsupported` from a device without a controller, a controller failure's reason passed through, and revocation taking effect immediately.

## Sharing to a device

**Android** registers `ShareActivity` for `ACTION_SEND`/`ACTION_SEND_MULTIPLE` (any MIME type), so Continuity appears in every app's share sheet. It shows a bottom sheet listing connected devices, plus "All connected devices" when there's more than one; opening it starts the foreground service if it wasn't running, and the list fills in as trusted devices reconnect. Shared files are copied to app-private cache first (a share's read grant only lasts as long as the receiving activity, and the engine streams from a real path), then sent as normal file transfers. Shared text or a link goes to the chosen device's *clipboard* via `EngineCommand::SendText` — an ordinary `ClipboardUpdate` sent to just that peer, so it works with v1 peers too.

**Desktops** don't give an unpackaged tray app a real Share menu slot (macOS needs a signed Share extension bundle, Windows 11's Share button needs a packaged MSIX app, Linux has no common share menu), so each gets the closest native equivalent (`core/continuityd/src/share.rs`):

- **Linux**: right-click entries in Files/Nautilus (Scripts → Send with Continuity → device), Dolphin (a service-menu submenu) and Nemo (one action per device), written to the user's data directory.
- **Windows**: Explorer's **Send to** menu, one `Continuity - <device>` shortcut per device.
- **macOS**: Finder's **Open With → Continuity**, declared via `CFBundleDocumentTypes` in the app's `Info.plist`, which hands the file to the running app; it then asks which device with a native list dialog (AppleScript's `choose from list`, with device names passed as arguments rather than spliced into the script).

On Linux and Windows the entries are per *connected* device (plus "All connected devices" once there's more than one), kept in sync as devices connect and drop, and removed when Continuity quits (and again at startup, in case it didn't quit cleanly) — the menu itself is the device picker, and it only ever offers something that can work right now. Each entry runs `continuityd --share-to <device id | all> <files...>`, which hands the files to the already-running instance and exits without starting a second tray app. The hand-off is a one-line JSON request over a loopback TCP port, authenticated with a random token published in a file only the user can read (`share-endpoint.<profile>.json` next to the trust store), so another local account can't push files out through it. Folders are skipped (the engine only sends regular files).

## Known gaps (tracked, not bugs)

- Desktop keychain persistence has all three backends enabled (macOS/Windows/Linux — see Identity above), but only macOS's has been confirmed against real persistence; Windows/Linux are compile-checked in CI only, same confidence level as the rest of those platforms' unverified pieces.
- File transfer auto-accepts from any trusted peer with no per-transfer prompt — reasonable given only paired devices can reach it, but a future version could add an explicit accept/reject step like the pairing flow has.
- The Android device page's player progress slider and volume bar (see Now-playing metadata above) are confirmed to compile, render correctly (screenshotted on a real emulator, including the redesigned empty states), and launch without crashing, but dragging the slider to actually trigger a `Seek` was never exercised against a live paired connection — the Android emulator's default NAT networking doesn't relay mDNS multicast between host and guest, and there's no manual "enter IP" fallback in the pairing UI to work around that.
- iOS build is unverified (no Xcode on this dev machine) — see `docs/ios-build.md` for exactly what's left.
- Android's outbound clipboard sync is foreground-only per the OS restriction above; no in-app affordance yet nudges the user to bring the app forward when they want to push a copy.
- `SyncEvent::PeerActivity` (see Connection health in shells above) is only rendered on Android so far — desktop's tray menu has no per-device list UI to show it in yet, and `continuityctl` deliberately doesn't log it (too frequent, one per peer per ping interval).
- The network-change watcher (see Discovery above) polls every 10s rather than using each OS's native change-notification API — real Wi-Fi/VPN switch reaction has only been exercised via the local IP address changing on this dev machine, not against Android's `ConnectivityManager` or a real mobile network transition.
- Remote control (see above): Windows input injection/screen capture and Linux's xdg-desktop-portal + PipeWire implementation are both unverified against a real session. Linux's portal handshake is now tested against a mock portal (and its earlier never-completes bug fixed), but the rewritten PipeWire capture half hasn't been compiled here — only checked against the `pipewire`/`libspa` crates' source — so CI's Linux job is its first build, and a real GNOME/KDE desktop the first run. macOS screen capture is confirmed working for real; macOS input injection is confirmed *gated correctly* (Accessibility trust denial genuinely blocks it) but not confirmed to land clicks/keystrokes in the right place, since granting that trust needs a human in System Settings this environment can't provide.
- Android's remote-control UI is confirmed to compile and build into a real APK, but was never exercised against a live paired session — same emulator-networking limitation (no mDNS relay between host and guest, no manual-IP fallback) as the media progress bar above. The engine-level protocol/session logic it depends on *is* covered by a real two-engine test.
- Remote control's keyboard bridge only sends lowercase letters, digits, space, enter, and backspace — no shift, uppercase, symbols, or arrow keys yet.
- The controller UI uses direct tap/drag-to-mouse mapping, not a relative "trackpad" mode — precise pointing on a small phone screen controlling a much larger desktop is harder than it would be with the latter.
- No true extended-desktop support (a real second monitor a window manager could place windows onto) — deliberately out of scope, see "Remote control" above for why.
- Remote unlock is Linux-only, and its logind backend is compile-checked only (no live graphical session here). The phone-side Unlock button only needs the phone itself to be unlocked; requiring a fingerprint/PIN on the phone first would be a sensible tightening.
- The desktop share entry points (Linux file-manager entries, Windows Send To shortcuts, macOS Open With) and the Android share sheet are unverified on real devices. The Linux entry generation and the `--share-to` hand-off are covered by tests; the Windows shortcut code (COM `IShellLinkW`) is checked against the `windows` crate's real signatures but never compiled here. Thunar and Caja get no entries yet.
